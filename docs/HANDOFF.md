# Pulse BTC 5M 项目交接文档

本项目是 Windows 本机运行的 Polymarket BTC 五分钟 UP/DOWN 控制台。文档描述代码行为；实时配置和运行状态以对应页面 API 和 SQLite 为准。接手时先看本文件、仓库根目录的 AGENTS.md、git status 和相关测试。

## 架构与入口

| 层 | 入口及职责 |
| --- | --- |
| 前端 | React 19 + Vite 6。src/main.jsx 接收 SSE 快照并按路由挂载页面；src/api.mjs 处理本地接口。样式在 src/styles.css。 |
| 服务 | Node.js >= 24.5、Express、ESM。server/index.mjs 绑定本机 127.0.0.1，默认 3100，创建独立模拟和实盘引擎。 |
| 执行 | server/previous-direction-engine.mjs 实现上场方向策略；server/engine.mjs 管理入场、订单去重、资金、预测、结算；server/strategy.mjs 计算盘口深度与手续费。 |
| 交易所 | server/polymarket.mjs 对接 Polymarket SDK、市场、盘口、认证、下单和余额；server/price-feed.mjs 管理官方 Chainlink 流。 |
| 后台 | server/history.mjs 补齐历史；server/redemption.mjs 处理实盘自动兑换；保留的区间引擎为共享图表提供支撑/压力参考。 |
| 数据 | 内置 node:sqlite，WAL 模式。server/store.mjs、server/schema.sql 定义业务表和迁移；server/reports.mjs 用 SQL 汇总。 |

## 下单优先级

1. 任一策略运行时，开盘前 12 秒及开盘后 0–15 秒进入保护时段。服务优先调度正在运行的模拟、实盘引擎。开盘前预取下一场市场信息，不再为即将结束的场次发起新的盘口请求。
2. 开盘后并行核对市场接单状态及获取新盘口；仅在当前场次、条件 ID 和各方向代币一致时复用预取结果。预取失败则按市场、盘口的正常顺序请求，绝不使用上一场盘口。
3. 入场优先处理上一场结果与必要的预测、盘口、风险和实盘可用余额。上一笔实盘成交未确认会阻止下一单，因此成交核对属于执行依赖。无须等待最终结算，但有未结订单时必须有可靠预测才能推算资金序列。
4. 历史补拉、旧订单最终结算、展示余额和兑换等不会出现在下单等待链。保护时段暂停发起这些后台请求，历史接口只读现有数据；当前 BTC 参考价的常规 HTTP 刷新也让路。K 线报价复用现有 Polymarket WebSocket；target 由两盘共用的限时只读查询异步提供，不加入下单等待链。后台不能取消已经发送的请求；交易所响应和本机调度仍会影响实际延迟。
5. 兑换还避开下一场开盘前 30 秒，提交前再检查。无明确确认的交易不会假定到账或重复提交。低优先级任务恢复后自动续跑。

市场发现、必要费用信息和双向盘口通过 `Polymarket.readPublic` 走只读快速恢复：每次SDK查询设置总取消信号及单次超时2500毫秒、`retries:0`，由已有交易检查调度重试；市场请求失败后的轮询间隔为1秒，成功恢复10秒，盘口继续下一轮重查。共享同一价格源和fetch实现的实例只合并并发中、同场同条件及同代币集合的读取，响应分别复制；成功数据不做完成后缓存，不跨场复用盘口。HTTP429按 `Retry-After` 保持同键冷却（未给出时1秒），冷却立即返回错误、不阻塞引擎。错误保留Gamma/CLOB具体阶段及底层网络代码。上述机制不适用于下单、签名、账户认证或兑换，不改变入场条件、资金、价格新鲜度和成交核对。详见 [官方接口恢复](MARKET_CONNECTIVITY.md)。

## 策略与执行

三连亏跟随模拟使用 LF-005。每轮触发只成交一单，使用配置的首笔金额。成交即结束本轮，无论该单最终获胜、失利或作废，只累计跟随成交场次之后的来源盘新订单。再次触发须有三笔新的连续失利。因来源跳场、盘口或风控暂未成交时，本轮继续等待。已成交订单按原流程预测和结算，未结算支出仍计入风控敞口。历史 LF-004 的同向失利跳场及加倍规则可在离线脚本回放。

三连亏跟随实盘使用 LF-003。触发的三笔来源成交须来自三个相邻且同向的市场，若本轮首笔跟随也反买该方向并失利，则跳过紧接的一场，下一场恢复入场检查。拦截记录 `LOSS_FOLLOW_FIRST_LOSS_COOLDOWN` 包含三笔来源场次和首笔跟随场次。历史订单保留各自的策略版本。

三场同向反买模拟使用 SR-001。仅在开盘后 15 秒内检查紧邻的三个已结束市场，三场均 UP 买 DOWN，均 DOWN 买 UP。官方结果优先，未结算时用下单前已保存的同源预计结果。缺失、作废和不同向均不下单。复用 PR-002 的跳场逻辑，再次跳场只读取本盘上一场的实际成交和胜负。每场最多一笔，固定使用 10 pUSD 含手续费预算；卖一 0.40–0.65，逐档最高 0.65。模拟成交按盘口档位、tick、深度和最小份额检查，保留单笔上限、余额与累计止损。固定金额不等待上一笔的资金序列预测，未结算敞口仍计入止损。首次初始资金 10,000 pUSD、累计止损 1,000 pUSD，默认暂停。

两场同向反买模拟使用 SR-002。紧邻两个已结束市场同向即检查反买入场，包含刚形成的连续两场。同向延续且本盘上一场反买的成交确认或预计失利时，跳过一场，再重新检查紧邻两场。沿用 SR-001 的 15 秒窗口、固定预算、买价、风控和结算规则，首次初始化也使用相同默认值。

两盘共用 `StreakReverseEngine`，复用 `PreviousDirectionEngine` 的行情和执行机制。共享上场方向模拟的市场历史、已保存预测和 BTC 行情采集，预测查询通过来源引擎去重。图表经同一套 SSE 数据提供历史与实时 K 线、target 和支撑压力。不创建新的 Chainlink WebSocket。账户、风控配置、订单、结算及日志分别写入独立数据库。

- 上场方向两盘固定反买紧邻上一场，刚形成连续两场同向时跳过紧接的一场。模拟盘 PR-002 在同向延续期间，若紧邻上一场有当前会话的实际反买成交且确认或预计失利，就再跳过本场；再下一场恢复入场检查。未成交无需再次跳过。实盘 PR-001 每段走势只跳一次。反向、作废或数据缺失打断同向计数。
- 官方结果优先；未结算可用 Polymarket 起止价或同源末秒/收盘前最后一笔预测。无有效方向或官方作废的上一场不可用，不跳场选更早结果。最近 40 场同反向比较只供参考。
- 开盘 0–15 秒入场，每场最多一次。检查所选方向卖一价在各自可配置的范围内（默认 0.40–0.70，包含两端），按 tick、深度、手续费和最小份额检查；订单各档成交价受上限约束。实盘的最低价是下单触发条件。
- 马丁规则：从首笔金额开始，预计失利加倍，预计获胜回首笔；超过单笔上限或最大加倍次数从首笔开始。余额、止损和待确认状态会限制新单。后续以官方结算核对并记录差异。配置、资金序列、日志与订单分别保存；页面启动时使用最新输入的首笔金额。
- 模拟按真实盘口逐档估算成交。实盘使用 Polymarket CLOB 提交一笔 FOK，只有官方成交确认才记入持仓。成交核对按订单 ID 匹配官方账户成交，兼容 CONFIRMED 和 TRADE_STATUS_CONFIRMED；MINED 和其他未最终确认状态继续等待。提交超时进入待核对，不能重发；可从交易记录补填官方订单 ID。程序不自动做链上授权。
- 账户认证依赖 .env 的 POLYMARKET_PRIVATE_KEY、POLYMARKET_WALLET_ADDRESS 和 LIVE_TRADING_ENABLED。SDK 派生 CLOB 凭据；刷新实盘页会通过本机受控接口自动尝试连接 Polymarket；配置缺失则跳过，已认证复用连接，开盘保护时段延后。连接不启动策略。钱包面板可手动重读配置和余额，无需重启。有待结订单或策略正在运行时禁止切换钱包。
- 自动兑换仅处理由当前功能记录了所属钱包且已官方结算、有兑付的本程序订单。填写 .env 的 POLYMARKET_RELAYER_API_KEY 和 POLYMARKET_RELAYER_SIGNER_ADDRESS，再刷新钱包。链上确认后刷新余额；提交不明需人工核对。历史盈亏以结算时间归属，兑换到账并不重复计入盈亏。没有真实链路的测试结果时，不把模拟测试表述为已实测成交/兑换。

三连亏跟随模拟只监控上场方向模拟当前账户会话中已成交的订单，按订单连续计亏，未下单不打断；作废、获胜或未知打断。开盘前用已有同源报价和官方起始价预判当前单，开盘后只用已结束的来源订单复核。官方结果优先，尚未结算可用同源预测。跟随盘沿用来源入场方向、跳场逻辑和价格范围，独立保存模拟资金和订单。单笔金额上限、资金余额及累计止损限制入场。新一轮的预算固定，已有跟随单的预测和结算在后台继续。默认暂停，共享行情 WebSocket 和图表配置。

三连亏跟随实盘 `/loss-follow-live` 与模拟版共用 `LossFollowEngine`，按模式选择策略版本。两盘都读取 `/previous` 模拟盘的连续失利、市场方向和买价范围。跟随模拟沿用 PR-002 的入场节奏，跟随实盘按 PR-001 检查来源跳场。新盘首次初始化复制 `/previous-live` 当时的首笔、单笔上限、最大加倍次数及累计止损。使用独立配置、触发、订单与成交核对账本，默认暂停并利用现有实盘钱包连接与启动确认。余额由实际钱包提供，同钱包的策略共享该余额。自动兑换检查两个账本的同钱包提交记录，V1 按条件、V2 按份额复用同一笔链上交易。已明确失败或结果不明的交易继续遵循原兑换核对规则。

跟随盘离线研究入口为 `node scripts/backtest-loss-follow.mjs`，默认使用 LF-005。可用 `--legacy-lf001` 回放旧纯翻倍规则，或用 `--legacy-lf004` 回放同向失利跳场规则。报告包含全部来源样本及 PR-001、PR-002 各自的子样本。脚本只读来源成交、预测、盘口和历史市场结果，复用跟随引擎在内存 SQLite 回放，结果另存 `data/loss-follow-research/<时间戳>/report.json`。成交机会限于来源有成交且保存盘口的场次。旧规则的方法和样本局限见 [LF-001 2026-11-24 回测](research/LF-001-backtest-2026-11-24.md)。

布林模拟与上场方向震荡区间模拟已从菜单、模拟报表及任务调度移除，旧路由与接口均返回 410。两份旧账本保留。历史规则见 [布林模拟归档](BOLLINGER.md) 与 [震荡区间模拟归档](LEVEL_LIMITED.md)。其余交易页继续共用图表的支撑位和压力位。

## 页面与数据

- 侧栏分为顶部 Logo、中间 `.sidebar-menu` 和底部 `.sidebar-bottom`。Logo 和 BUILT FOR/账户区域固定，中间菜单独立滚动，窄屏使用图标菜单。`src/pages.mjs` 中标记 `group: 'data'` 的历史场次、模拟盘报表和实盘报表在交易页面之后同组显示，顶部以分割线区分。
- 页面名称与固定英文唯一标识集中定义于 `src/pages.mjs`，侧栏每个页面菜单的中文名下方显示其ID，菜单DOM同时提供 `data-page-id`。`previous`＝上场方向模拟，`loss-follow`＝三连亏跟随模拟，`streak-reverse`＝三场同向反买模拟，`streak-reverse-two`＝两场同向反买模拟，`previous-live`＝上场方向实盘，`loss-follow-live`＝三连亏跟随实盘，`market-history`＝历史场次，`reports`＝模拟盘报表，`reports-live`＝实盘报表。ID与路由同名，跨页面关联使用ID。小屏收起文字时可通过菜单悬停标题识别ID。各页面通过右侧策略控制的「高级参数与风险限额」进入本页设置，使用帮助保留在顶栏。配置归属各自页面及账本。
- 术语「震荡区间」统一指下支撑位至上压力位的完整区间（含两端），中间蓝色区域是其中一个子区域。

- 模拟盘、实盘和区间参考后台复用同一条 Polymarket Chainlink WebSocket；各行情消费者独立读取报价增量，交易状态、配置、订单和账本继续分开。前端通过本盘 `/api/events?chart=1` 的一条 SSE 同时接收状态及具名的 `chart-prices/history/opening/range` 事件；行情生产独立于策略快照，先回放共享行情库与内存近31分钟报价、官方target及区间，不等待策略轮询或进入下单等待链。`server/ui-stream.mjs` 共用发送及清理逻辑，旧 `/api/events` 及 `/api/chart-events` 保留兼容。
- `src/page-stream.mjs` 在标签页隐藏或离开时释放SSE，重新可见后重连、回放并刷新状态；服务器交易持续运行。历史圆点暂停隐藏页轮询。避免多个页面各占两条HTTP/1.1长连接，耗尽同源连接池而拖慢分页及刷新。`src/coalesced-refresh.mjs` 合并同查询的历史版本刷新：在途请求完成后最多补一次最新查询，只有分页/筛选/模式切换或卸载才取消旧查询，防止连续取消造成空等。订单及日志分页响应提供 `Server-Timing: db;dur=...`，用于区分SQLite处理与浏览器排队；诊断及验证见 [页面请求性能](UI_PERFORMANCE.md)。
- 本场视图开盘最多给官方 target 预留 2 秒；期间 target 已到可与首点同时画出，超时则先画本场实时点，收到官方起始价后补线。若先收到本场开盘边界（时间戳恰等于开盘时刻）的同口径官方流报价，立即画「target · 待核对」，不以附近报价替代；官方起始价到达后覆盖。策略已读取的当场官方起始价也可发布到共享图表。暂定线仅供展示，不计算本场涨跌，不参与交易或预测。近 30 分钟视图不等待。target 首次读取官方事件 priceToBeat，缺失时读取同口径官方 crypto-price 的 openPrice；已知口径时并行重试这两个官方来源。图表有订阅者时共享报价连接可独立重连。每次连接有独立的 15 秒接收窗口；过期缓存和心跳不会重置此窗口或反复关闭刚建的连接。共享区间只用于图表；两盘设置中的「支撑位 / 压力位回看时间」共用并持久化，默认 60 分钟，允许 15–1440 分钟（每 5 分钟一档），沿用 5 分钟实体 K 线和原计算滞后。「中间蓝色区域占比」也共用并持久化，通常默认 60%（升级沿用此前图表比例），允许大于 0% 至 100%，剩余宽度在上下两侧均分。开盘保护期间停算；本场未就绪时，两盘均可沿用紧邻上一场同口径的支撑位、压力位和底色，标明来源。本场结果到达后一起更新；预言机口径变化或跨过一场时不沿用。
- 历史列表为 41 场已结束市场 + 当前场。绿 UP、红 DOWN、灰待定；当前场实时预估有虚线圈，上一场预测有红色图钉，官方结果更新后去掉。两盘已成交且预计失利时，本场虚线圈变成反转黄，上一场的待结算预测加黄色反转实线圈并保留红钉。统计只计官方结果。圆点支持悬浮详情和 Polymarket 深链接，模拟盘和实盘都用同样的 B 标记标出各自已成交的场次；待确认、未成交及拒单不标。
- 历史接口先返回 SQLite 记录，缺失/未结算由后台补拉。同源价格、起始价、预测、入场快照、拦截依据分别存储，已确认数据不因切换场次或接口异常消失。
- 独立历史场次页 `/market-history` 用 `GET /api/market-history?date=YYYY-MM-DD` 读取一个北京时间自然日，默认今天，只显示已结束的五分钟场次。左侧标注开盘小时，小时组按 23 时至 00 时倒序，组内也按开盘时间倒序。所选日期内连续至少 5 场已核验同向时，整段方格加金色外框，右上角标注整段场数。顶部最长同向统计也包括不足 5 场的已核验连续段，UP 和 DOWN 并列时显示两个方向，两者均无已核验方向时显示破折号。连续段跨小时计算，方向变化、缺场、待核验和作废打断计数。悬停、聚焦或点击可见起止价及高亮段场数。前后日、日期选择和今天按钮共用北京日期工具。手动刷新显示转动图标和结果提示，后台核验进度单独展示。
- `MarketHistory` 先读取共享核验缓存和原有市场历史、预测、起始价、方向记录。没有核验标记的结果用虚线显示。缺失和待核验的场次由后台按场次去重，最多 20 场一批，使用 Gamma 场次元数据和官方结算查询。有结算结果但 Gamma 缺起止价时，按同一场次和官方预言机口径从 Polymarket crypto-price 补查，对比 Gamma 已有价格。官方起止价齐全且与官方方向一致，或官方作废且起止价齐全，才写入 `verified_at`。已核验记录直接复用，只计这些场次为最终结果。核验和补查避开开盘保护窗口，读接口不等待外部请求。接口失败或结果不完整时保留现有记录和已获得的价格，至少 60 秒后重试。

## 运行与维护

- 安装依赖：npm ci；开发模式：npm run dev；生产模式：npm run build，然后 npm start。Windows 日常使用仓库启动/停止批处理，后台日志在 data/server-out.log 和 data/server-error.log。
- 开发模式由 Express 同一个本机端口承载页面、API 和 Vite 刷新 WebSocket。保存页面引用的 `src/*.mjs`、JSX 或 CSS，浏览器收到相应的热更新或刷新。SQLite 和运行日志目录排除在 Vite 文件监视与静态文件访问之外。修改 `server/*.mjs` 后由维护者选择合适时机重启服务。生产模式提供已构建的 `dist`，前端变动需重新构建。启动批处理检测到已有服务时沿用其模式。
- 校验：npm run check、npm test、npm run build。执行规则的测试用固定时间和假的交易所接口；验证不得提交真实订单或启动实盘。
- 修改运行中的服务前先核对实盘状态。未要求暂停正在运行的实盘时不要为了部署而中断；服务重启后不自动恢复实盘。数据库、私钥、API 凭据不进入 Git 和日志输出。
- 复用现有组件与 ESM 风格。历史订单原因和原始证据不得用现在的策略重写。避免为轻量修改引入新框架。上场方向的规则变化必须先在 server/strategy-versions.mjs 追加不可改写的版本记录，再切换启用版本；只调整参数时沿用策略版本，由 config_id 区分。模拟和实盘均在下单占用时写入策略版本，结算不改写。
- **每次改变功能、策略、API、数据库、配置或运维流程，在同一次改动同步更新本文件和相关专项文档。** 更新入口和用户操作可同时改 README。陈旧规则移到归档并注明与运行版本的区别。
