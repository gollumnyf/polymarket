## 2. 项目用途与技术栈

本项目是本机运行的 Polymarket BTC 五分钟 UP/DOWN 交易控制台，提供模拟交易、实盘交易、市场历史、运行日志和模拟报表。模拟成交依据真实盘口深度计算，不是固定 0.5 成交。

| 项目 | 当前实现 |
| --- | --- |
| 运行环境 | Node.js >= 24.5.0，使用内置 `node:sqlite` |
| 前端 | React 19、Vite 6、JSX、lucide-react |
| 后端 | Node.js ESM `.mjs`、Express 5 |
| 市场客户端 | `@polymarket/client`，当前声明版本 0.17.0；viem |
| 数据库 | SQLite，WAL，业务字段分列、按用途分表 |
| 测试 | Node 内置 `node:test`、`node:assert/strict` |
| 主开发环境 | Windows PowerShell；原工作区 `F:\Program\VibeCoding\polymarket` |
| 默认服务地址 | `http://127.0.0.1:3100` |
| 依赖版本依据 | `package.json` 与 `package-lock.json`；不要随意升级 SDK |

没有 TypeScript、ORM、全局状态框架或现成的端到端浏览器测试套件。不要为了小改动引入大框架。

## 4. 关键业务名词

| 名词 | 含义 |
| --- | --- |
| 场次 `round` | 5 分钟场次开盘 Unix 秒，必须对齐 300 秒 |
| `end` | 通常 `round + 300`，Unix 秒 |
| 创建/结算/采样时间 | Unix 毫秒；不要与 round 秒数混算 |
| 市场结果 | 该场市场 UP/DOWN，与本账户有没有下单无关 |
| 订单输赢 | 下单方向与官方兑付结果的关系 |
| 预计结果 | 尚未最终结算时，根据该场有效起止价格或同源采样推算 |
| 首笔金额 | 马丁资金序列的基数，页面启动时同时保存最新输入 |
| 蓝色区域 | 当前支撑与压力之间扣除两侧边界带后的可入场区域 |
| 暂停新单 | 入场被条件拦截；策略仍在运行，采集、预测、结算继续 |
| 暂停策略 | 用户主动暂停账户执行，与暂停新单不同 |

金额和份额沿用六位小数的 `money()` 处理。市场价格是大于 0、小于 1 的份额价格；“50”通常指 50¢，代码值为 0.50。BTC 参考价格和份额价格不是同一个量。

## 5. 区间策略：当前有效规则

### 5.1 默认参数

这些是代码默认值，不是对当前数据库实际配置的承诺。运行中的参数以对应 API 状态及 SQLite 当前配置为准。

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `streakReverseEnabled` | true | 是否启用连续同向反买 |
| `streakReverseRounds` | 3 | 本场紧前必须连续同向的场数 |
| `lookbackHours` | 2 | 初次选向的市场 UP/DOWN 统计窗口 |
| `levelLookbackHours` | 4 | 支撑/压力历史窗口 |
| `levelLagMinutes` | 15 | 区间计算向前平移，排除最近 15 分钟 |
| `edgePercent` | 20 | 每一侧边界带占区间宽度百分比 |
| `resumeRounds` | 2 | 边界暂停后恢复需要的连续收盘确认数 |
| `executionMaxPrice` | 0.55 | 常规区间策略滑点后成交硬上限 |
| `breakoutPercent` | 0.1 | 突破距离占参考区间宽度百分比 |
| `breakoutRounds` | 2 | 连续收盘突破确认场数 |
| 区间入场延迟 | 0 秒 | 开盘立即尝试，但仍须满足全部条件 |
| 区间入场检测窗口 | 120 秒 | 页面按分钟配置；超时不追单 |

基础 `DEFAULT_CONFIG` 还有旧策略默认值，不要直接把其中 entryDelay/entryWindow/maxPrice 当作 range 的最终值；检查专用引擎和账户配置。

### 5.2 支撑、压力和蓝色区域

1. 采用已结束的 **5 分钟实体 K 线**，实体由官方开盘价、终止价组成，不使用影线最高/最低。
2. 默认使用向前平移 15 分钟后的近 4 小时窗口，共 48 根实体 K 线，取实体最低/最高作为支撑/压力。
3. 每个五分钟场次结束重算；当前未结束场次不会改变自己的历史边界。
4. 不要求往返次数、触及次数、次峰触及门槛或区间最大宽度门槛。
5. 设支撑为 L，压力为 U，每侧比例为 e：蓝色下沿 `L + (U-L)*e/100`，蓝色上沿 `U - (U-L)*e/100`。
6. 入场价格必须严格大于蓝色下沿、严格小于蓝色上沿；等于任一边界不满足。
7. 图表与交易判断必须使用同一组**当前滚动支撑/压力**。`breakoutReferenceLower/Upper` 是突破计数参考线，不能用它计算蓝色区域。

### 5.3 边界暂停与恢复

- 到达边界带或区间外：暂停新单，已有订单继续结算，不关闭策略。
- 返回蓝色区域后，默认需要连续两个已结束场次的收盘价都严格在蓝色区域内；不是要求整场都在区域内。
- 中间缺失、作废、等于边界或收盘在区域外都不能凑成连续确认。
- 只统计符合暂停后恢复条件的已结束场次，下单前再检查当前价仍在蓝色区域。
- 从下支撑侧返回，常规恢复方向买 UP；从上压力侧返回买 DOWN。中部继续沿用这个方向，直到再次触边再按返回侧选向。
- 保留原马丁资金序列，不因为边界暂停而恢复首笔金额。

### 5.4 连续同向反买：禁止回退历史触发

当前开盘场次为 R、配置为 N，只读取：

```text
R - N*300, R - (N-1)*300, ... , R - 300
```

例如本场 10:00、N=3：只能使用 09:45、09:50、09:55 三场。

- 全部 UP → 本场买 DOWN；全部 DOWN → 本场买 UP。
- 不含当前未结束场次；缺一场、作废或方向不同均不触发。
- 未最终结算时允许使用**对应市场场次**的预计结果，官方最终结果随后优先核对。
- 不能跳过缺失场次找更早一场，不能搜索更早的同向片段，也不能因旧事件有效而延续旧反买触发。
- **每个新场次重新检查紧前 N 场**。不满足时回到常规区间逻辑，不代表整个策略停机。
- `range_streak_events` 是审计记录，不是当前选向的回退池。
- 触发后优先选向，但仍须满足蓝色区域、边界恢复确认、每场一单、入场截止和资金限制。
- 该规则下取消策略的 0.50 触发价、0.55 成交硬上限和相对滑点限制；仍检查有效价格、tick、真实深度、最小份额及手续费预算，不能买入价格为 0 或 1 的盘口。
- 报价后及实际提交前需再核对当前条件；不能使用已失效反买规则取得的宽松报价继续下单。

“连续同向反买已启用”是配置说明，不等于本场已触发。实际依据见 `entrySignal.streakSignal`；因蓝色区域被拦截时可能只返回 `lockedStreak` 作为解释依据，不能据此绕过 `code` 或无方向状态。

### 5.5 常规区间选向和突破

- 首次区间选向按近配置小时数内的已结束五分钟市场结果统计多数方向，不统计账户订单盈亏。
- 同票时取紧邻上一场市场结果的反方向；未最终结算可用该场预计结果，不能跳过上一场去找更早结果。
- 区间基础方向保存后沿用，边界返回按上述恢复规则更新方向。
- 突破必须同时满足距离和连续场数，默认距离为参考区间宽度的 0.1%，连续两个已结束场次收盘严格越过同一条线。
- 上穿线：`参考压力 + 参考宽度 * 0.1/100`；下破对称计算。不是 BTC 价格本身的 0.1%。
- 初次越线时固定突破计数的参考上下界，避免每场移动边界吞掉突破；不把多次场内穿越算作多个场次。
- 中断连续性需要重新检查/计数，不能在一个周期内累计不相邻的两次突破。
- 已确认突破仍不能绕过边界暂停。旧突破在回到参考区间或进入新的滚动蓝色区域时按现有状态机退出，已记录的恢复确认要求保留。
- 常规买入要求有效卖一严格 `< 0.50`；触发后可按深度成交至配置硬上限（默认 `<= 0.55`）。不再按相对滑点百分比拦截常规 range。

## 6. 马丁资金、预测和订单执行

- 首笔金额可配置，点击启动时保存当前输入并以最新金额启动，不再设置独立“保存首笔金额”按钮。
- 预计失利后下一场按资金序列加倍；任意一场获胜恢复首笔金额，不要求累计盈亏回正。
- 达到单笔金额上限时按代码条件进入新的首笔周期；最大加倍次数、余额等仍独立检查，不能把“错误不停机”理解为放弃所有限制。
- 后续买入尽量按上一单预计结果及时推进，不等待官方最终结算；真实盈亏只按官方兑付结算，预测与实际不一致须保留核对信息。
- 起止价接口未返回时，优先同源末秒采样；末秒缺失则向前追溯收盘前最近有效报价。记录实际采样时间和来源，不能拿收盘后的报价冒充终止价。
- 追溯价格可以来自更早采样时刻，但“市场场次连续性”仍以每个目标 round 独立判断，不等于允许跳过场次。
- 当前进行中的场次也展示根据最新有效官方价格计算的实时预计结果。
- 每个模式每场最多一次下单：数据库占用 `order_rounds` 与订单唯一约束共同保证。拒单、清空历史、隐藏、重启都不能绕开占用而重发同场订单。
- 实盘 placing/confirming/uncertain 必须核对，成交不明时不得盲目重发。
- 普通接口错误、预测/结算请求失败、盘口暂不可用：记录具体原因并后续重试，不自动关闭账户运行状态；不满足条件的交易仍应拦截。
- 未下单原因必须写明实际原因、场次、时间及有关数值，避免用“原因 A 或原因 B”这种不能定位的描述。

## 7. GAM 的实际实现范围

`GamMvEngine` 基于 `MomentumEngine` 执行路径，独立模拟账户。根据模型公允价值与所选盘口卖一价格的差判断方向，遵守该执行路径的官方价格校验和最高 0.50 买价规则，不继承 range 的 0.55 硬上限或连续反买规则。

当前限制必须如实告知后续开发者：

- 模型系数在 `gam-mv-engine.mjs` 内定义，尚无完整训练和在线更新流程。
- OFI 输入固定为 0。
- 页面有目标残差、均值方差、双边报价/套利观察指标，但未接入自动对冲、再平衡或双边套利下单。
- `gamSignal` 未全部写入独立结构化模型信号表；新订单会通过 `entry_reason` 保存当时模型估值、盘口与阈值说明，不代表全部模型特征已有结构化存档。

不要仅因页面有指标，就宣称对应交易功能已实现。

## 8. 历史记录、隐藏和下单原因

### 市场历史

- 最近 40 场官方结果用圆点显示，UP 绿、DOWN 红，未确认灰；旁边统计 UP/DOWN 数量。
- 点击圆点打开对应 Polymarket event；悬浮显示场次、起止价、变化、数据来源、预测差异和相关交易/拦截情况。
- 已知起止价能够预测方向，不代表市场已经官方结算，不能为消除灰圈伪造最终结果。
- `RoundHistory` 的结算查询每批最多 20 个 condition ID，40 场应分批；单批失败不得丢掉成功批次和已取得价格。
- 页面缓存每次快照合并 SQLite 中的新结果，防止后台已确认结果被旧 pending 内存缓存遮挡。
- 缺失数据不能清空已存价格，pending/unavailable 不能覆盖 resolved/void；新的有效价格可以补齐已结算记录。
- 信号采样默认保存 5、10、15、20、35、40、45、50、55、60 秒及配置入场秒数。反转标记使用相应规则下的实际/采样依据，不能一直固定 5 秒。

### 交易与日志

- 分页由服务端执行，默认每页 20 条，可选 10/20/50；不要一次拉取全部记录再前端分页。
- SSE 主要传快照、待处理订单及历史版本，分页列表根据版本变化更新。
- 交易表包含下单时间、最终结算时间、预测结果、净盈亏；当前场次、上一场次有特殊标识。
- 当前标签的“隐藏”把该模式已有全部记录标记为隐藏，不受当前页或状态筛选限制；新记录默认可见。
- `orders.is_hide`、`logs.is_hide` 为 0/1。共享 system 日志用 `system_log_visibility` 按模式隔离。
- “恢复显示”取消对应标签隐藏标记；不再使用 localStorage 把整个组件永久收起来。
- 隐藏只影响列表可见性，不影响结算、资金、每场占用、报表、完整导出或市场历史圆点。
- “清空”与隐藏不同：模拟历史清空会删除允许删除的旧记录；交易清空保留待处理订单和 `order_rounds`。不要将两个动作混淆。
- 展开订单首项显示“下单原因”。新订单在占用时将当时策略/价格/资金依据写入 `orders.entry_reason`，后续结算或配置更新不得改写。
- 旧单仅按已存证据还原并标明“历史依据还原”；证据不足明确提示未保存，不能拿当前信号补写旧原因。

### 报表

`/reports` 当前只统计区间模拟。默认近 30 天，按 Asia/Shanghai 日历展示，单次最多 366 天；展示期间总盈亏、手续费、单量等。SQL 聚合，不一次加载全部订单。隐藏记录仍计入报表。

## 10. 数据库结构与不可破坏的数据

基础 schema 当前版本为 **10**：v9 加入记录级隐藏，v10 加入 `entry_reason`。`RangeStore` 还有自己的建表/补列逻辑，不能只修改 `schema.sql` 就假定旧库已升级。

| 表组 | 用途 |
| --- | --- |
| `accounts`、`account_sessions`、`strategy_configs` | 账户、会话、配置版本 |
| `orders`、`order_rounds` | 交易及独立场次占用 |
| `order_events`、`order_trade_ids` | 状态变更和平台成交标识 |
| `order_books`、`order_book_levels` | 下单盘口证据 |
| `order_predictions`、`round_predictions`、`round_openings` | 订单预测、市场预测、官方起始价 |
| `ticks`、`round_signals`、`round_history` | 行情、指定秒信号、市场结果 |
| `entry_blocks`、`entry_diagnostics`、`entry_diagnostic_levels` | 精确拦截原因与盘口证据 |
| `logs`、`log_clear_positions`、`system_log_visibility` | 运行日志与模式独立的清空/隐藏 |
| `range_configs`、`range_control`、`range_regimes` | range 配置版本、当前状态及区间历史 |
| `range_market_prices`、`range_price_bars`、`range_votes` | 官方起止价、价格段和市场统计 |
| `range_order_signals` | 每单对应区间及选向证据 |
| `range_streak_events`、`range_streak_samples` | 连续反买触发事件与逐场依据 |
| `range_streak_order_signals`、`range_streak_order_samples` | 每单固定的反买依据 |

新增业务数据应分表、分列，不把整段业务对象塞进 JSON/body 列。内存对象、API JSON 与数据库结构化存储不是同一个要求。订单 ID、资产 ID、condition ID 用 TEXT，避免数字精度损失。

重要规则：

1. `Store` / `RangeStore` 构造函数会迁移、暂停账户并处理异常订单，**不是只读查看工具**。不得对运行中的正式库随意 `new Store(path)` 做排查。
2. 读取正式数据库使用 `new DatabaseSync(path,{readOnly:true})`，不要写入临时测试数据。
3. 不删除 WAL/SHM 来“修复”数据库。运行中复制主 sqlite 文件不保证备份一致；停服务后备份，或使用正确的 SQLite 一致性备份方法。
4. 数据迁移应可重复启动、保持外键一致、保留旧记录/配置/会话。用临时库测试旧版本升级、重启和数据完整性。
5. 隐藏、结算、历史回补不能重写原订单触发样本和下单原因。
6. 不为解决显示问题执行 `DELETE`、重置账户或清空历史。

只读检查例子（在项目目录执行）：

```powershell
node --input-type=module -e "import {DatabaseSync} from 'node:sqlite'; const db=new DatabaseSync('data/range.sqlite',{readOnly:true}); console.log(db.prepare('SELECT MAX(version) AS version FROM schema_migrations').get()); db.close();"
```

## 11. 编码风格与开发规范

- JavaScript ESM，后端和纯逻辑 `.mjs`，React 组件 `.jsx`；命名沿用 camelCase，数据库列 snake_case。
- 使用单引号、分号和两空格缩进；现有短表达式和对象比较紧凑，修改时贴近邻近代码，不顺便格式化整个文件。
- **CSS 每条选择器规则一行**，即 `.class{属性:值;属性:值;}`；不是每个属性单独一行。保持 `src/styles.css` 的既有格式。
- 中文界面和业务错误说明；代码注释解释原因、边界条件和不变量，避免重复翻译代码。
- 文件用 UTF-8，保留中文。PowerShell 写文件要明确编码，不能用错误的默认编码破坏源码；BAT 变更需验证 cmd 兼容性与换行。
- 不引入大面积机械格式化、无关重命名、无关依赖升级或通用化重构。
- 业务计算尽量为纯函数，市场访问留在 venue/engine，SQL 留在 Store，组件只负责展示和交互。
- UI 共用组件优先，新增页面必须明确 API 前缀、mode、数据库归属。
- Hooks 不要放在条件返回之后；异步 effect 清理定时器、请求和 SSE，防止卸载后回写。
- 异步操作防重复提交；旧快照不能覆盖新快照；账户/配置切换后的响应不能污染另一个页面。
- 数值参数验证类型、有限性、上下界和整数要求，不能接受字符串 `"true"` 冒充 boolean。
- SQL 参数绑定；动态表名只来自代码中的白名单。
- 交易关键路径不能因为网络失败无限等待；已有流程使用超时、独立任务和自动重试。
- 不要把内部实现术语直接当成用户流程；但拦截原因和订单证据须给出确切数据。
- 用户倾向直接完成明确授权的可逆修改，避免反复确认；有真实业务歧义时集中问清楚，不擅自改变策略含义。

## 12. API 与安全边界

常用接口（按页面添加相应 API 前缀）：

| 方法与路径 | 用途 |
| --- | --- |
| GET `/state` | 当前快照、账户、信号；控制令牌只供本机操作 |
| GET `/events` | SSE |
| GET `/history?mode=paper` | 40 场市场结果，实盘 mode=live |
| GET `/:mode/orders`、`/:mode/logs` | 分页列表；page/pageSize/status/anchor |
| POST `/:mode/start`、`/:mode/stop` | 启停策略 |
| POST `/:mode/config` | 配置更新 |
| POST `/:mode/orders/visibility`、`/:mode/logs/visibility` | `{hidden:true/false}` |
| POST `/paper/orders/clear`、`/paper/logs/clear` | 模拟历史清空 |
| GET `/:mode/export`、`/:mode/logs/export` | 完整 CSV，包括隐藏记录 |
| GET `/paper/report` | 区间模拟报表，使用 `/range/api` |
| GET `/health` | 服务身份、进程和项目目录 |
| POST `/service/shutdown` | 服务关闭 |

服务只监听本机；Host、Origin、`X-Control-Token` 防护必须保留。浏览器请求自动携带 Origin；脚本调用控制接口必须明确提供匹配的 Origin 和当前令牌。服务重启后旧令牌失效。

不要打印完整 `/state` 返回对象，因为含控制令牌；诊断只挑必要字段。不要读取或输出 `.env` 中的私钥/钱包凭据，不把凭据、真实数据或带令牌的 remote 放入文档、日志、提交和前端。

实盘需要本地配置凭据、`LIVE_TRADING_ENABLED=true` 及用户主动启动；开发、查看行情、构建和测试都不需要启动实盘。

## 14. 更新运行服务的顺序

1. 先完成代码与相关测试。
2. 查询 `/api/health`，核对项目根目录和服务身份。
3. 只记录所需字段：三套账户的 running、session、configId；不要输出令牌。
4. 如果实盘正在运行，不在无人确认情况下自动中断并重启/恢复实盘。先处理真实运行状态与用户授权。
5. 使用正常服务关闭流程，等待关闭数据库和在途任务；不要直接杀掉不明 PID。
6. 停止后备份三套 SQLite；如果仍有对应 WAL/SHM，一并保留。备份放 data 下带时间戳目录。
7. 启动服务，等待健康检查成功。历史重建可能使启动耗时增加，不能短暂未响应就认定失败。
8. 因本次维护暂停的模拟策略，只有此前已运行、且 session/configId 仍相同时才恢复；原来暂停的保持暂停。绝不顺便启动实盘。
9. 验证新 schema/API/信号已生效及账户状态，再向用户报告。不要仅以进程启动成功作为全部功能成功的证据。

## 15. 最近修复与禁止回归清单

| 症状 | 已定位原因 | 必须保留的修复 |
| --- | --- | --- |
| 蓝色区域跑到支撑/压力之外 | 使用旧冻结突破参考线计算蓝区 | 蓝区和入场统一使用当前滚动 L/U |
| 历史圆点长期变灰、显示数据丢失 | 40 个 condition ID 超过单次 20 上限；内存 pending 遮盖 SQLite 新结果 | 分批查询、部分失败保留、每次合并数据库结果 |
| 隐藏后新交易也不显示 | 旧方案是整个组件/localStorage 隐藏 | 记录级 is_hide；新记录默认显示 |
| 连续反买使用离本场较远的旧片段 | resolveStreak 回退到旧 trigger | 只用本场紧前 N 场；旧事件仅审计 |
| 展开记录不能解释为何买入 | 只有成交备注/部分证据 | entry_reason 下单时保存、后续不覆盖 |
| 保存/启动金额后资金序列不对应 | 客户端输入与服务端配置脱节 | 启动同时保存输入，提交后读服务端最新状态 |

已废弃或被覆盖的旧要求，不要恢复：

- RP-01 作为活跃策略。
- 恢复两个已移除的旧模拟菜单。
- 所有规则都绕过蓝色区域的连续反买。
- 最近 N 场不满足时沿用更早反买触发。
- 用订单胜负代替市场场次结果统计。
- 用 Binance 现货价格替代本场 Polymarket 官方参考价。
- 只保存在前端内存/浏览器里而不持久化关键业务依据。
- 将“接口错误不停策略”解释为可以跳过盘口、资金、时间、场次占用等限制。
