# 官方市场与盘口连接恢复

## 现象及诊断（2026-11-25）

用户看到「等待本场市场；fetch failed」。该面板分号前是市场发现状态，分号后是盘口状态；此组合的 `fetch failed` 来自盘口查询，不代表两项都失败。排查时各页面均已恢复，原日志只保存顶层错误，无法再还原那一次失败的DNS、代理或远端连接原因。近期另有历史预测查询HTTP429，不能直接认定它就是这次盘口失败的原因。

本机使用HTTPS_PROXY。只读探测官方Gamma市场和CLOB盘口均返回200，约898毫秒与656毫秒。现有SDK默认重试2次，通用fetch单次有10秒上限；已有市场信息时，一次刷新失败可能等常规10秒轮询才重查。慢请求及隐藏重试可能占用15秒入场窗口。

## 修改范围

`Polymarket.readPublic` 用于市场发现、市场费用信息和双向盘口：

- SDK每次操作使用2500毫秒取消信号、2500毫秒单次HTTP超时、`retries:0`。失败后交回原引擎下一轮检查，不在内部等待多次重试。市场刷新错误将轮询间隔降为1秒，成功恢复10秒；原先缺市场或盘口失败时也继续原调度重查。
- 同一共享价格源、同一fetch实现的实例，只共享相同键的在途Promise。市场键包含开盘场次，费用键包含条件ID，盘口键包含场次、条件ID、协议和完整代币集合。结果复制后各自使用，成功结果立即移出在途表，没有TTL缓存、没有跨场旧盘口兜底。
- HTTP429遵守SDK解析的 `retryAfter` 秒数，无有效值时至少1秒；同键冷却期间直接返回明确错误，不睡眠、不发新请求。过期冷却在后续调用中清理。
- 错误注明Gamma市场、CLOB费用信息或CLOB双向盘口，并保留底层 `ECONNRESET`、`ENOTFOUND`、`UND_ERR_SOCKET`、`TIMEOUT` 等代码。继续执行凭据脱敏，不输出请求鉴权头及钱包密钥。

不改策略方向、跳场、马丁、入场截止时间、买价范围、tick、深度、余额、盘口新鲜度和提交前校验。无有效数据继续等待，入场截止后仍跳过；不能保证外部网络中断时成交。签名、真实订单提交、账户认证、自动兑换及历史后台任务不接入此公共读取合并或重试，不增加真实订单重发。

## 验证

- 测试覆盖真实SDK网络错误只发送一次、错误代码保留、超时释放、成功后重新读取、并发读取合并与结果隔离、费用信息的短超时、429冷却，以及市场刷新失败一秒后恢复并按原规则只下一单。
- `node --test --test-isolation=none tests/*.test.mjs`：455项全部通过，测试仅用假交易所及内存账本。
- 三个独立实例共用行情源和传输，只读同时请求相同市场及盘口，实际仅发送2次网络请求：Gamma 200约678毫秒、CLOB 200约1256毫秒。未调用钱包、签名或下单。
- 已在入场窗口结束后更新运行服务，仅恢复原先运行的previous、loss-follow、level-limited模拟盘；实盘与布林模拟保持暂停。部署后间隔5秒检查全部5个交易页面，两次均无错误，市场有效、双向盘口采样年龄约0.7–1.4秒。

若仍反复报错，先按具体阶段与网络代码检查本机代理及对应官方域名连通性。HTTP429需等待限流恢复；HTTP403不能当作普通断连绕过。通用网络错误不会被当作已成交，也不会使策略自动停止。
